# 03: Crypto and Merkle spec

Exact formats for hashing, signing, the evidence log, Merkle trees, receipts, evidence bundles and verdict commitments. **Implement exactly this. Do not invent alternative encodings.** Shared implementation lives in `packages/shared` (`hash.ts`, `eip712.ts`, `merkle.ts`, `commit.ts`, `bundle.ts`) and is used by the gateway, API, merchant SDK, benchmark and the dashboard's browser verifier.

## 1. Conventions

| Topic | Rule |
|---|---|
| Hash function | **keccak256** everywhere |
| Off-chain JSON hashing | `keccak256(utf8(JCS(value)))` where JCS is RFC 8785 canonical JSON (library: `json-canonicalize`). No floats in hashed objects: use integers or decimal strings. |
| bytes32 / addresses | Lowercase `0x`-prefixed hex in JSON; addresses checksummed only for display and contract calls |
| Timestamps | Unix seconds as integers (uint64) |
| Token amounts | Decimal strings in JSON; bigint in code (USDC: 6 decimals) |
| Signatures | EIP-712 typed data, secp256k1 (65-byte r,s,v). Contract owners that are smart accounts are verified via ERC-1271 (OpenZeppelin `SignatureChecker`). |
| Domain separation | Every domain includes `chainId`; contract domain also includes `verifyingContract` |
| Zero hash | `0x` followed by 64 zeros (`ZERO32`) |

## 2. Mandate

### 2.1 On-chain struct and EIP-712 type

```
Mandate(
  address owner,
  address agent,
  address token,
  uint256 maxPricePerCall,
  uint256 totalBudget,
  uint64  expiresAt,
  uint256 nonce,
  bytes32 merchantsHash,
  bytes32 termsHash
)
```

Domain: `{ name: "RecourseEscrow", version: "1", chainId, verifyingContract: <escrow address> }`.

- `merchantsHash = keccak256(abi.encodePacked(merchants))` where `merchants` is the allowlist as `address[]` **sorted ascending** (encodePacked pads each element to 32 bytes; viem `encodePacked(['address[]'], [merchants])` matches Solidity).
- `termsHash = keccak256(utf8(JCS(terms)))` where `terms` is the off-chain JSON in 2.2.
- `mandateId` = the EIP-712 digest of the struct (`_hashTypedDataV4(structHash)`), which is also the key in the contract's mandate mapping.
- `nonce`: per-owner, single use (`nonceUsed[owner][nonce]`); prevents replay of a signed mandate.

### 2.2 Off-chain terms (bound by `termsHash`)

```json
{
  "version": 1,
  "category": "weather_data_api",
  "defaults": {
    "freshness_seconds": 3600,
    "schema_required": true,
    "substitutions": "not_allowed",
    "sla_ms": 5000
  },
  "discretion": ["vendor_choice"]
}
```

Hard limits (cap, budget, expiry, merchants) are on-chain; defaults and discretion are off-chain but cryptographically bound through `termsHash`. Zod schema: `TermsSchema` in `packages/shared/src/schemas.ts`.

## 3. Identifiers

| Id | Definition |
|---|---|
| `requestId` | bytes32. Generated by the gateway per client request as `keccak256(utf8(uuidv4))`, returned in `X-Recourse-Request-Id`; the agent reuses it when calling `createEscrow` and in the retry. |
| `escrowId` | `keccak256(abi.encode(mandateId, requestId))` computed in the contract; a repeated `requestId` per mandate reverts (`DuplicateRequest`). |

## 4. Evidence log entry

### 4.1 Fields

```json
{
  "seq": 42,
  "ts": 1767200000,
  "type": "response",
  "request_id": "0x...",
  "mandate_id": "0x...",
  "agent_id": "0x...",
  "payload_commitment": "0x...",
  "prev_hash": "0x...",
  "entry_hash": "0x..."
}
```

- `type` is one of: `request`, `payment_required`, `payment_proof`, `response`, `receipt`, `decision`.
- `seq` is a global, gapless counter starting at 1 (one chain per gateway instance in the MVP; per-agent chains are roadmap).
- `ts` is the gateway clock at capture time.
- `prev_hash` is the previous entry's `entry_hash`; the first entry uses `ZERO32`.
- `entry_hash = keccak256(utf8(JCS({ seq, ts, type, request_id, mandate_id, agent_id, payload_commitment, prev_hash })))`. `mandate_id` and `agent_id` are `null` when unknown (still included as `null` in the JCS object).

### 4.2 Payload fields per entry type

| Type | Fields (names are field-commitment keys) |
|---|---|
| `request` | `method`, `path`, `query`, `headers_hash`, `body_hash`, `merchant_id` |
| `payment_required` | `status` (402), `requirements` (object: scheme, chainId, escrow, token, merchant, amount, requestId, expiresAt) |
| `payment_proof` | `escrow_id`, `tx_hash`, `chain_state` (object read from chain: state, amount, merchant, windowEnds, block) |
| `response` | `status`, `headers_hash`, `body_hash`, `body_len`, `content_type`, `latency_ms` |
| `receipt` | `request_id`, `response_hash`, `timestamp`, `merchant`, `signature` |
| `decision` | `kind` (shortlist, rationale, choice), `data` (object) (agent-claimed; flagged as such in the UI) |

`body_hash = keccak256(raw body bytes)`; the raw bytes are stored in `blobs` keyed by `body_hash`.

## 5. Field commitments and selective disclosure

Goal: the arbiter (and a public verifier) can be shown only the fields needed, with proof they belong to the entry, and cannot brute-force hidden fields.

For each payload field `name` with JSON value `v`:

```
salt_i      = random bytes32 (stored privately in gateway `fields` table)
leaf_i      = keccak256(abi.encodePacked(salt_i, keccak256(utf8(name)), keccak256(utf8(JCS(v)))))
```

- Sort fields by `name` ascending, build `StandardMerkleTree.of([[leaf_0], [leaf_1], ...], ["bytes32"])`.
- `payload_commitment` = that tree's root. An entry with zero fields uses `ZERO32`.
- **Disclosure of a field** = `{ name, value, salt, proof }` where `proof` is the Merkle proof of `leaf` against `payload_commitment`.
- The verifier recomputes `leaf` from `name`, `value`, `salt`, then verifies `proof`.

Because every leaf is salted with a random 32-byte value, a guessable field (a price, a status) cannot be confirmed by brute force from the commitment alone.

## 6. Batches, Merkle tree, signed tree head, anchoring

### 6.1 Batching

A batch closes when `BATCH_MAX_ENTRIES` (default 16) entries are pending or `BATCH_MAX_SECONDS` (default 30) have elapsed, or when `POST /log/flush` is called (the API does this on every dispute). Each batch covers a contiguous range `[first_seq, last_seq]`.

### 6.2 Tree

```
tree = StandardMerkleTree.of(
  entries.map(e => [BigInt(e.seq), e.entry_hash]),
  ["uint256", "bytes32"]
)
root = tree.root
```

Store `tree.dump()` in `batches.tree_dump`. Proof for `seq`: `tree.getProof([seq, entry_hash])`. Note: `StandardMerkleTree` double-hashes leaves and uses sorted-pair hashing; do not mix other Merkle implementations.

### 6.3 Signed tree head (STH)

EIP-712 domain `{ name: "RecourseGateway", version: "1", chainId }`:

```
TreeHead(
  bytes32 root,
  uint64  size,        // cumulative number of entries up to and including this batch
  uint64  batchIndex,  // 0-based
  uint64  timestamp
)
```

Signed by `GATEWAY_PRIVATE_KEY`. Store `signature` in `batches`.

### 6.4 Anchoring

The gateway calls `escrow.anchorRoot(root, size, batchIndex)` (only the configured gateway address may call it). The contract stores `anchoredAt[root] = block.timestamp` and emits `RootAnchored(root, size, batchIndex, timestamp)`. Anchoring is idempotent per root.

### 6.4a Continuity

Continuity across batches comes from `prev_hash` linking (the first entry of batch n links to the last entry of batch n-1). Full consistency proofs between tree heads are roadmap.

## 7. Receipts (merchant-signed)

EIP-712 domain `{ name: "RecourseReceipt", version: "1", chainId }`:

```
Receipt(
  bytes32 requestId,
  bytes32 responseHash,   // keccak256(raw response body bytes)
  uint64  timestamp,
  address merchant
)
```

The merchant SDK signs after producing the response and returns it as `X-Recourse-Receipt: base64(JSON({ requestId, responseHash, timestamp, merchant, signature }))`. The gateway logs it as a `receipt` entry. A receipt proves **what the merchant claims it delivered**, so a later dispute cannot pretend the response was different.

## 8. Evidence bundle (`GET /evidence/:requestId`)

```json
{
  "version": 1,
  "chain": { "chain_id": 84532, "escrow": "0x...", "gateway": "0x...", "merchant": "0x..." },
  "request_id": "0x...",
  "mandate_id": "0x...",
  "escrow_id": "0x...",
  "entries": [
    {
      "entry": { "...": "all 9 fields from 4.1" },
      "disclosed": [ { "name": "status", "value": 200, "salt": "0x...", "proof": ["0x..."] } ],
      "batch_proof": { "batch_index": 3, "proof": ["0x..."] }
    }
  ],
  "tree_heads": [ { "root": "0x...", "size": 160, "batch_index": 3, "timestamp": 1767200100, "signature": "0x..." } ],
  "anchors": [ { "root": "0x...", "tx_hash": "0x...", "block_number": 123, "block_timestamp": 1767200110 } ],
  "receipt": { "requestId": "0x...", "responseHash": "0x...", "timestamp": 1767200000, "merchant": "0x...", "signature": "0x..." }
}
```

Zod schema `EvidenceBundleSchema` in `packages/shared`. Response bodies are not inside the bundle; they are fetched by `body_hash` via `GET /evidence/blob/:bodyHash` and verified by rehashing.

## 9. Verification algorithm (used by the arbiter and by the browser verify page)

Implemented in `packages/shared/src/bundle.ts` as `verifyBundle(bundle, opts) -> VerificationReport`. Steps and report keys:

1. `entry_hash_ok`: for each entry recompute `entry_hash` from the 8 JCS fields and compare.
2. `fields_ok`: for each disclosed field recompute `leaf` and verify its proof against `payload_commitment`.
3. `membership_ok`: verify the entry's `batch_proof` against the batch `root` (uint256, bytes32 leaf).
4. `tree_head_signature_ok`: recover the signer of each tree head and compare with `chain.gateway`.
5. `anchor_ok` (optional, needs RPC): `anchoredAt(root) != 0` and equals `anchors[].block_timestamp`.
6. `receipt_ok`: verify the receipt signature recovers `chain.merchant` and that `responseHash` equals `keccak256(body)` of the blob.
7. `chain_ok` (only when the full batch export is supplied): consecutive `prev_hash` linking across the batch.
8. `time_ok`: the anchor time is not earlier than the entries' `ts`, and the dispute time is after the payment.

`VerificationReport = { entry_hash_ok, fields_ok, membership_ok, tree_head_signature_ok, anchor_ok | null, receipt_ok | null, chain_ok | null, time_ok, errors: [] }`. Any failure of steps 1 to 4 or 6 makes the evidence **invalid**; the adjudicator then returns `needs_human_review` with reason `evidence_invalid`.

**Tamper test:** the verify page runs the same function in the browser on the full batch export. Editing one byte of any entry field changes `entry_hash`, breaks `membership_ok` and `chain_ok`, and the corresponding check turns red.

## 10. Verdict commitment

```
commitment = keccak256(utf8(JCS({
  dispute_id,
  escrow_id,
  evidence_root,        // root of the anchored batch(es) covering the evidence (array if multiple: sorted)
  rule_results_hash,    // keccak256(JCS(rule_results))
  claims_hash,          // keccak256(JCS(claims))
  models,               // [{ role, name, digest_or_version }]
  prompt_hash,          // keccak256 of concatenated prompt files, in fixed order
  settings_hash,        // keccak256(JCS({ temperature, seed, top_p, ... }))
  outcome,              // "REFUND" | "RELEASE"
  fault                 // "NONE" | "AGENT" | "MERCHANT"
})))
```

Posted in `resolve(escrowId, outcome, fault, commitment)`. The full verdict JSON is stored off-chain (`verdicts` table) and is replayable: re-run the rules and models with the stored settings and compare commitments. LLM nondeterminism can still differ across hardware; the commitment proves *what was decided and on which inputs*, not bit-exact reproducibility.

## 11. Replay, ordering and time rules

- Mandates: EIP-712 domain separation, `nonce` single-use, `expiresAt` enforced by the contract.
- Escrows: unique per `(mandateId, requestId)`.
- Receipts and tree heads: domain includes `chainId`; receipts bind `requestId`.
- Ordering: `seq` is gapless; a gap in an exported batch is evidence of tampering (`chain_ok = false`).
- Clock: `ts` is the gateway clock, anchoring time is the chain's `block.timestamp`; verification only requires the anchor to be later than the entries.

## 12. Trust windows and honest limits

- **Pre-anchor window:** between an event and its batch being anchored (default up to 30 seconds), the gateway operator could in principle alter data. This is a stated trust assumption; mitigations are short batches, merchant receipts (the merchant signs independently) and roadmap witnesses or TEE.
- The log proves captured data was not changed *after* anchoring; it does not prove the agent was right, and it cannot prove nothing bypassed the gateway. Say "tamper-evident", never "tamper-proof".
- The gateway sees only traffic routed through it. The merchant SDK may optionally require a gateway-signed header (`X-Gateway-Sig`, Should-tier) to reject requests that bypassed it.
